# DocScanX 身份解析引擎（IPE）完整设计文档

## 一、核心定位

### 1.1 引擎名称
**IPE - Identity Parsing Engine（身份解析引擎）**

### 1.2 核心目标
将散乱的实体（姓名、身份证、手机号等）智能关联，判断哪些实体属于同一个人，最终输出**人员档案**而非字段列表。

### 1.3 与传统工具的本质差异

| 维度 | 传统扫描工具 | DocScanX IPE |
|-----|-------------|--------------|
| 处理单位 | 字段 | 自然人 |
| 关联能力 | 无 | 跨文档身份追踪 |
| 输出内容 | "身份证×156" | "涉及23人" |
| 合规对应 | 需二次换算 | 直接对应法规 |

## 二、标识分层体系

### 2.1 标识类型定义

| 层级 | 标识类型 | 代码 | 权重 | 说明 |
|-----|---------|------|------|------|
| 第一层 | 身份证号 | ID | 1.0 | 17位+校验位，中国唯一标识 |
| 第二层 | 手机号 | PH | 0.9 | 11位，实名制 |
| 第三层 | 姓名+地址 | NM+AD | 0.6 | 组合使用 |
| 第四层 | 姓名+手机 | NM+PH | 0.7 | 组合使用 |
| 第五层 | 仅姓名 | NM | 0.3 | 需辅助验证 |

### 2.2 标识优先级决策表

| 身份证 | 手机号 | 姓名 | 最佳策略 | 基础置信度 |
|-------|-------|------|---------|-----------|
| ✅ | ✅ | ✅ | 身份证为主，多字段验证 | 0.95 |
| ✅ | ❌ | ✅ | 身份证+姓名同段落 | 0.90 |
| ✅ | ✅ | ❌ | 身份证+手机号 | 0.85 |
| ❌ | ✅ | ✅ | 手机号+姓名同段落 | 0.80 |
| ❌ | ✅ | ❌ | 仅手机号 | 0.60 |
| ❌ | ❌ | ✅ | 仅姓名（标记残缺） | 0.30 |

## 三、关联规则库

### 3.1 核心规则

| 规则编号 | 规则名称 | 触发条件 | 置信度 | 行为 | 聚合说明（面向用户展示） | 示例 |
|---------|---------|---------|-------|------|-------------------------|------|
| R01 | 同段落强关联 | 姓名+身份证，同段落，距离<50字 | 0.95 | 直接合并 | "张三"和身份证在同一段落出现（相距<50字），判定为同一人 | 合同第3段："甲方：张三，身份证号310101199001011234" → 归为一人 |
| R02 | 同段落中关联 | 姓名+手机号，同段落，距离<30字 | 0.85 | 候选合并 | "张三"和手机号在同一段落出现（相距<30字），归属同一人 | 员工表第2行："张三，手机号138xxxx5678" → 归入候选 |
| R03 | 表格同行关联 | 姓名+身份证，同表格行 | 0.90 | 直接合并 | 表格中"张三"和身份证在同一行，判定为同一人 | 员工花名册表格中，某行同时包含"张三"和身份证号 → 归为一人 |
| R04 | 同文档跨段落 | 姓名+身份证，同文档不同段落 | 0.70 | 候选合并 | 文档中"张三"和身份证分别在两个段落，但同属一份文档 | 第2页提到"张三"，第5页出现其身份证号 → 归入候选 |
| R05 | 手机号+身份证 | 手机号+身份证，同段落 | 0.85 | 候选合并 | 手机号和身份证在同一段落，推定同属一人 | 第10段："联系电话138xxxx5678，身份证号310xxx" → 归入候选 |
| R06 | 地址辅助验证 | 与已有档案地址完全匹配 | +0.10 | 提升置信度 | 地址与已有档案中某人的地址一致，增加归属置信度 | 新发现的"浦东新区xx路"与张三已有地址一致 → 置信度+0.10 |

### 3.2 互斥规则

| 规则编号 | 规则名称 | 触发条件 | 行为 | 聚合说明（面向用户展示） |
|---------|---------|---------|------|-------------------------|
| E01 | 身份证不同 | 两个档案身份证号不同 | 强制不合并 | "张先生"的身份证号与"张三"不同（310xxx≠440xxx），判定为不同人 |
| E02 | 性别冲突 | 身份证性别位与姓名/上下文矛盾 | 降低置信度 | 身份证号码第17位指示性别为"男"，但上下文称谓为"女士"，置信度降低 |
| E03 | 地区冲突 | 身份证前6位与地址矛盾 | 降低置信度 | 身份证前6位为"110000（北京）"，但地址是"上海市浦东新区"，置信度降低 |

## 四、置信度计算

### 4.1 计算公式

```
Score(P) = CF_base × Σ(W_k × E_k) × Context_Multiplier + Bonus - Penalty

参数说明：
  CF_base            = 基础置信度（基于标识组合）
  W_k                = 第k个标识的权重
  E_k                = 标识是否存在（1 or 0）
  Context_Multiplier = 位置系数（同段落=1.0，跨段落=0.8）
  Bonus              = 辅助加成（同地址+0.10，多字段+0.15）
  Penalty            = 惩罚项（性别冲突-0.20，地区冲突-0.15）
```

### 4.2 置信度决策阈值

| 置信度范围 | 决策 | 行为 |
|-----------|------|------|
| ≥ 0.85 | 高置信度 | 直接合并为同一人 |
| 0.60-0.85 | 中置信度 | 放入候选队列，可人工确认 |
| < 0.60 | 低置信度 | 独立档案，标记需复核 |

## 五、人员档案结构

### 5.1 档案字段定义

```json
{
  "person_id": "P00001",
  "primary_identifier": {
    "type": "ID",  // ID/PH/NM
    "value": "310xxx199001011234"
  },
  "identifiers": {
    "names": ["张三", "张先生"],
    "id_cards": ["310xxx199001011234"],
    "phones": ["138xxxx5678"],
    "addresses": ["上海市浦东新区xxx"]
  },
  "evidence": {
    "high_confidence": [
      // 各证据项结构（同理由规则 R01~R06，互斥规则 E01~E03）
      {
        "rule": "R01",                    // 触发此聚合的规则编号
        "rule_description": "同段落强关联", // 规则名称
        "aggregation_reason": "张三和身份证在同一段落出现（相距<50字），判定为同一人", // 面向用户解释
        "source_text": "甲方：张三，身份证号310101199001011234", // 原始文本片段
        "source_file": "合同A.docx",
        "source_location": "第3段",
        "confidence": 0.95
      }
    ],
    "medium_confidence": [...], // 中置信度证据链
    "low_confidence": [...]    // 低置信度证据链
  },
  "linked_files": [
    {"file": "合同A.docx", "location": "段落3"},
    {"file": "员工表B.xlsx", "location": "表格第5行"}
  ],
  "completeness": 4,  // 信息完整度 1-5
  "confidence": 0.92,  // 综合置信度
  "risk_level": "HIGH", // LOW/MEDIUM/HIGH/CRITICAL
  "status": "CONFIRMED", // CONFIRMED/PROVISIONAL/PENDING
  "warnings": []  // 数据质量告警
}
```

### 5.2 信息完整度评分

| 字段数 | 完整度评分 | 说明 |
|-------|-----------|------|
| ≥4字段 | 5分 | 极高完整度 |
| 3字段 | 4分 | 高完整度 |
| 2字段 | 3分 | 中完整度 |
| 1字段 | 2分 | 低完整度 |
| 仅姓名 | 1分 | 信息残缺 |

### 5.3 风险等级定义

| 等级 | 标准 | 说明 |
|-----|------|------|
| CRITICAL | 4+字段 + 置信度≥0.90 | 高度可识别，风险极高 |
| HIGH | 3字段 + 置信度≥0.85 | 可明确识别 |
| MEDIUM | 2字段 + 置信度≥0.70 | 有一定识别性 |
| LOW | 1字段或置信度<0.60 | 识别性较弱 |

## 六、处理流程

### 6.1 整体流程

```
输入：文档文本 + OCR结果
         ↓
    实体识别 (UIE)
         ↓
    实体列表 + 位置信息
         ↓
┌─────────────────────────────────────────┐
│           标识优先级判断                 │
│                                         │
│   优先用身份证号                         │
│       ↓ 无或不足                         │
│   优先用手机号                           │
│       ↓ 无或不足                         │
│   使用姓名+地址等辅助组合                 │
└─────────────────────────────────────────┘
         ↓
┌─────────────────────────────────────────┐
│           候选对生成                     │
│                                         │
│   For each pair of entities:            │
│     If can_link(entity_a, entity_b):    │
│       calculate_confidence()            │
│       add_to_candidate_pairs()          │
└─────────────────────────────────────────┘
         ↓
┌─────────────────────────────────────────┐
│           关联规则执行                   │
│                                         │
│   High confidence → Direct merge         │
│   Medium confidence → Candidate queue    │
│   Mutual exclusion → Never merge        │
└─────────────────────────────────────────┘
         ↓
┌─────────────────────────────────────────┐
│           身份图谱构建                   │
│                                         │
│   Nodes: entities                       │
│   Edges: relationships + confidence      │
│   Components: persons                   │
└─────────────────────────────────────────┘
         ↓
    人员档案列表
         ↓
    报告生成
         ↓
输出：敏感信息扫描报告
```

### 6.2 实体关联伪代码

```python
def link_entities(entities):
    # Step 1: Sort by position (paragraph)
    entities.sort_by_position()
    
    # Step 2: First pass - strong associations
    for entity in entities:
        if entity.type == 'ID' or entity.type == 'PH':
            # Look for name in same paragraph
            name = find_name_in_paragraph(entity.paragraph)
            if name:
                create_link(entity, name, HIGH_CONFIDENCE)
    
    # Step 3: Second pass - cross-paragraph
    for entity in entities:
        if entity.type == 'ID':
            # Look for name in same document
            name = find_name_in_document(entity.document)
            if name:
                create_link(entity, name, MEDIUM_CONFIDENCE)
    
    # Step 4: Build identity clusters
    clusters = build_clusters()
    
    # Step 5: Merge clusters
    for cluster_a, cluster_b in clusters:
        if can_merge(cluster_a, cluster_b):
            merge_clusters(cluster_a, cluster_b)
    
    return clusters
```

## 七、边界情况处理

### 7.1 正常场景

| 场景 | 处理方式 | 置信度 |
|-----|---------|-------|
| 丈夫张三+儿子张章子，身份证不同 | 两个独立档案 | - |
| 同姓名+同身份证 | 合并为同一人 | 0.95 |
| 同姓名+不同身份证 | 不合并，标记矛盾 | - |

### 7.2 异常场景

| 场景 | 处理方式 | 用户提示 |
|-----|---------|---------|
| 同姓名+同身份证 | 合并 | ⚠️ 发现疑似重复人员 |
| 不同姓名+同身份证 | 不合并 | ⚠️ 数据异常：同一身份证对应多人 |
| 仅姓名，无其他信息 | 建立残缺档案 | ⚠️ 信息不完整，建议补充 |

## 十、设计哲学

| 原则 | 说明 |
|-----|------|
| **身份证优先** | 最权威的标识，作为主线索 |
| **多字段验证** | 单字段不足时，组合提升置信度 |
| **诚实透明** | 数据质量问题明确告知用户 |
| **不过度设计** | 不追求100%准确，接受合理误差 |
| **可追溯** | 每一步关联都有证据链支撑 |
